Collaboration no longer resends the document with every edit.

**@gotipe/collaboration.** The provider sends only the operations the server has not confirmed, without the baseline, in frames of at most 512 KiB with one in flight. A large document or a long offline session no longer exceeds GoTipe Cloud's 1 MiB message limit and falls into a reconnect loop. Pass the whole `collaboration_state` as `initialState`: its new `generation` names the baseline, the provider connects with the `gotipe.v2` subprotocol, and Cloud refuses a replica of a replaced document at the handshake (`onBaselineReplaced`). Without a `generation`, or with a server that selects `gotipe.v1`, the provider still works as before and repeats the baseline in each frame. The provider keeps one acknowledged clock instead of every operation ID and no longer parses the whole log on each keystroke. Typing is merged into at most one frame per 50 ms and 300 frames a minute, so a connection stays under the server's default message rate. Operations restored from a local copy under another peer ID are sent once at the handshake. An operation or baseline that cannot fit into a message is reported through `onError` and stops the provider instead of reconnecting forever. `CollaborationState` has an optional `generation`; keep it with a local copy.

A frame ends only after a whole transaction, so other editors never receive half an edit (a heading without its `level`), which their schema would refuse. A transaction larger than a frame goes whole up to 1 MiB; a larger one, such as a long paste, goes as parts flagged `continues` that GoTipe Cloud saves, acknowledges and relays together, and sends again whole after a disconnect. Over `gotipe.v1` such a transaction is reported and stops the provider. After the server error `UPDATE_TOO_LARGE` the provider sends that edit again in standalone frames, and a relayed piece the editor's schema refuses waits until the rest arrives; `DOCUMENT_TOO_LARGE` stops the provider. The ACK deadline starts once the socket has sent the frame, and only a confirmed save resets the reconnect attempts. `applyCollaborationState` applies the stored updates as one update, so their order no longer matters and a record that depends on a later one loads. After a remote update the provider sends local repairs at once.

**@gotipe/core, @gotipe/wasm.** `editor.getCollaborationUpdate()` still returns the full state. New: `getCollaborationUpdate({ after, maxBytes })` returns only this replica's operations after a Lamport clock, and `getCollaborationUpdate({ missingFrom })` the operations a peer's full state lacks. Both are `gotipe.crdt/2` updates without the baseline, which `receiveCollaborationUpdate` accepts next to `gotipe.crdt/1`. The WASM engine exports `get_local_update_after` and `get_update_missing_from`; use matching versions of `@gotipe/core` and `@gotipe/wasm`.

Marks now have the same order on every replica, the order they were applied in: a peer no longer receives `[bold, italic]` for `[italic, bold]`, exported JSON and HTML nesting are identical between peers, and collaborative undo and redo keep the author's order. A repeated update no longer replays the whole log. A block added inside a block another peer deleted meanwhile, such as a cell of a deleted row after a concurrent column insert, is deleted with it instead of moving to the top level, where the schema refused it and stopped synchronization on both replicas; undoing the delete brings it back. After a remote update that changed a table, the editor repairs its grid (`normalizeTableGeometry`) in a transaction outside the undo history that every replica receives; cells it adds get the same IDs on every replica, so concurrent row, column and merge edits leave valid, identical tables.

Text a peer typed into an inline atom it did not know (a mention, inline math, a custom emoji, an inline image) loses the atomic marks when it arrives: `receiveCollaborationUpdate` dispatches the repair as a local transaction outside the undo history, so every replica receives it and the replicas converge. `getCollaborationUpdate({ after, maxBytes })` results now carry `continues` and end at transaction boundaries.

**@gotipe/wasm.** `export_html`, `export_markdown` and `sanitize_html` are removed: `@gotipe/core` serializes HTML and Markdown and sanitizes HTML in TypeScript on both engines. The module no longer contains `gotipe-export` and ammonia and shrinks from 604,875 to 298,588 bytes gzipped.

**@gotipe/sdk.** `Document.collaborationState` has the optional `generation` returned by GoTipe Cloud.

**GoTipe Cloud.** `GET /v1/documents/{id}` returns `collaboration_state.generation`. `/sync` accepts `gotipe.v2` with a `generation` parameter next to `gotipe.v1`; both kinds of client can edit one document. Updates are stored without the baseline, and the server merges a document's stored updates into one record as they accumulate, absorbing older records that repeated the baseline; the merge runs beside the room, at most two at once per process. A transaction sent in parts is buffered per connection up to `SYNC_TRANSACTION_LIMIT` (16 MiB by default, at most 30 MiB, new variable; eight such per process) and saved as one record; more gets `UPDATE_TOO_LARGE`, and an error on any part, a disconnect or a 30-second pause drops it unsaved. A save that would make a document's stored state larger than reads apply (60 MiB) gets `DOCUMENT_TOO_LARGE`. Records written by this version are `gotipe.crdt/2`: upgrade every API process together, and upgrade `@gotipe/collaboration`, `@gotipe/core` and `@gotipe/wasm` in your app with the server, because a client older than this release cannot replay `gotipe.crdt/2` updates from REST.
